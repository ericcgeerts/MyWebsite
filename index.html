Architecture decisions

Design behavior, tradeoffs, and limits
Check the application before showing “ready.”Reliability

Instance health is only the first check. The launcher waits for the game service and protocol response before publishing joining details. A boot delay or failed startup stays visible as a startup problem.

The tradeoff: readiness takes longer than simply exposing an IP address, but players receive an application-level signal rather than an infrastructure status.

Separate temporary compute from saved worlds.Data lifecycle

Persistent world data lives beyond the runtime. The normal shutdown path stops the game and checks its S3 backup before termination. Recovery paths retain the instance or create a snapshot when verification fails.

The tradeoff: recovery can retain storage or compute longer than a normal session. Backup verification is a design safeguard, not a guarantee against every data-loss scenario.

Make cleanup part of the design.Operations

Concurrency limits, idle shutdown, and session deadlines reduce accidental compute use. A watchdog reconciles expired or unexpected states. Cleanup is part of the lifecycle rather than a reminder to the operator.

The tradeoff: stored worlds, snapshots, networking, and control-plane requests continue to incur charges between sessions.
